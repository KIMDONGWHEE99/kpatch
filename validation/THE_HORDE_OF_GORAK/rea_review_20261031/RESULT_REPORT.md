# The Horde of Gorak REA 사용 점검

후속 상태: 아래 평가는 패치 제작 당시의 기록입니다. 이후 사용자의 연결 수정 요청으로 Ghidra 설정을 복구했고 현재 대화에서 32/64비트 예제의 실제 함수 분석까지 성공했습니다. [후속 연결·분석 결과](../../REA_GHIDRA_20261031/RESULT_REPORT.md). 게임 제작 당시의 Ghidra 실패 이력과 미완료 QA 범위는 그대로 유지합니다.

2026-10-31. 이번 패치의 보존 기록과 이전 Soulash 2의 실행 도구·평가서를 비교했습니다. 새 게임 실행이나 코드 재분석은 하지 않았으며, 연결 상태만 한 차례 확인했습니다.

**REA는 실제로 사용됐고 실행 실패 원인 조사·저장 보호·실행 모듈 문구 조사에 기여했습니다. 다만 직접 연결된 모든 분석 기능이 준비된 것은 아니었고, 조사 범위와 시간 배분도 더 효율적으로 운영할 여지가 있었습니다.**

## 이전 방식과 이번 방식

| 구분 | 이전 Soulash 2 | 이번 The Horde of Gorak |
|---|---|---|
| 요청을 보내는 방법 | PowerShell에서 Python 실행기·세션 도구를 거쳐 REA 호출 | 대화에 연결된 REA 도구를 직접 호출 |
| 분석 환경 | 별도 실행기가 Ghidra·Java 경로를 전달 | 현재 대화의 REA 서버 환경을 사용. 이전 실행기의 설정이 자동으로 이어지지 않음 |
| 실제로 얻은 근거 | Ghidra 코드 분석으로 표시 문구·저장 경계 조사 | 실행 파일 구조·문구 자원 조사와 Frida(실행 중 동작 관찰 도구) 관측. 세부 기계어 판독에는 Capstone을 병행 |
| 일반 파일 작업 | PowerShell·Python 등 사용 | PowerShell·Python 등 사용. 추출·번역 반영·패키징은 직접 연결 이후에도 이 방식이 적합 |

이번의 “현재 화면에서 사용”은 이 대화가 REA에 직접 요청을 보내는 방식입니다. 게임 화면을 캡처하고 마우스로 조작한 작업은 별도의 컴퓨터 조작 도구가 담당했습니다. REA 직접 연결과 화면 조작을 같은 기능으로 계산하지 않았습니다.

이번에도 깊은 코드 분석을 복구하기 위한 별도 실행 시도가 있었습니다. 따라서 전체 작업이 명령 실행을 전혀 사용하지 않은 것은 아닙니다. 중요한 차이는 **REA를 쓰기 위해 사용자가 별도 PowerShell 실행기를 먼저 준비할 필요가 줄었다는 점**입니다. 연결 방법이 바뀌었다고 분석 엔진 자체가 더 정확해지는 것은 아닙니다.

## 실제 기여와 확인한 한계

1. **수정한 게임이 처음 실행되지 않는 원인을 찾았습니다.** 실행 관측과 별도 기계어 판독을 연결해 DAT 자료의 검증값 계산 규칙을 확인했습니다. 이를 정상 재계산하도록 수정한 뒤 게임을 실행했습니다. 검사 분기를 없애서 우회한 변경은 아닙니다.
2. **검수 중 사용자 저장을 보호할 근거를 확보했습니다.** 실제 저장 경로·Steam 초기화 경로를 조사하고, 검수 사본에 한정한 보호 코드를 넣었습니다. REA 실행 관측과 실행 전후 파일 비교를 함께 사용했습니다. 운영체제 전체의 쓰기를 확인한 것은 아닙니다.
3. **실행 모듈에 들어 있는 문구와 사용 위치를 조사했습니다.** 파일 구조·자원·함수 연결 정보가 문구 수정의 근거가 됐습니다. 최종 176필드 수정과 Windows 자원 읽기 대조는 별도 제작·검증 도구의 결과입니다.

본문 855위치의 번역, 한글 글꼴 제작, 이미지 4곳 편집, 화면 배치 수정, 설치기 제작을 모두 REA의 성과로 계산할 수는 없습니다. 각각 전용 추출 도구·Python·Windows 글꼴 기능·실제 화면 검수가 기여했습니다.

**Ghidra(실행 파일을 읽기 쉬운 코드로 분석하는 도구)는 이번 직접 연결 환경에서 준비되지 않았습니다.** 현재 확인에서도 설치 경로 설정이 전달되지 않은 상태입니다. 별도 복구 시도에서는 한글 경로 처리 문제, 임시 경로 접근 제한, 연결 준비 응답 지연이 기록돼 있습니다. 마지막 시도는 내부 자동 분석이 약 56초에 끝났지만 연결 준비가 330초 제한에 도달하여, 사용할 수 있는 함수 분석 응답이나 재사용 결과를 얻지 못했습니다. 이를 Ghidra 분석 성공으로 판단하지 않았습니다. 필요한 부분은 Capstone(기계어 명령 판독 도구)과 실제 실행 관측으로 보완했습니다.

REA의 기본 파일 조사·실행 관측이 작동한 것과 Ghidra 심층 분석이 가능한지는 별개입니다. 현재 REA 6.8.0 연결 응답은 정상이며 열린 정적 분석 대상과 정리 대기는 없습니다. 이번 점검에서 전역 연결 설정은 변경하지 않았습니다.

## 효율 평가

직접 연결은 필요한 기능을 대화에서 선택하고 응답을 바로 이어서 조사하기 편합니다. 반복 파일 작업은 PowerShell·Python에 남기는 방식이 이 프로젝트에 더 적합합니다. 복잡한 함수의 복원이 필요한 경우에는 Ghidra 연결을 먼저 해결해야 하며, 직접 연결이 안 될 때는 준비된 별도 실행기를 대체 경로로 사용할 수 있습니다.

그러나 이번에는 실행 모듈에서 얻은 방대한 문자열 후보의 분류와 세부 조사가 계속 커졌습니다. 24,733개 후보를 담은 조사 목록도 있었지만 여기에는 명령·숫자·내부 자료가 포함돼 있어, 실제 화면의 번역 문구 수를 뜻하지 않습니다. 연결 방식을 바꾼 것만으로 이전의 범위 확대 문제가 해결되지는 않았습니다. 이 부분은 제작자인 제가 질문의 범위를 더 좁히고, 답을 얻은 조사 결과를 재사용했어야 합니다.

다음 작업에서는 일반 추출 도구로 해결되지 않는 구체적인 질문에 직접 REA를 사용하고, 답이 수정·확인으로 이어졌는지 판단하는 방식이 적절합니다. 예를 들어 “왜 후보가 실행되지 않는가”, “이 문구가 저장 이름에도 쓰이는가”, “실제 저장 경로는 어디인가”처럼 질문을 제한할 수 있습니다. 필수 출처 조사와 미해결 항목은 계속 기록하되, 후보 수나 호출 횟수를 성과로 삼지 않습니다.

이번과 이전 작업은 게임 구조·번역 규모·최종 확인 범위가 다르며 같은 조건의 비교 실험이 아닙니다. **이번 방식이 몇 배 빠르거나 비용이 몇 % 줄었다고 계산할 근거는 없습니다.** 추가 검수 중단과 개인용 마무리 요청에 따라 전체 출처 분류·엔딩·전체 분기·확장 설치 복구 시험은 미완료로 남았습니다. REA 사용량으로 이 완료 범위를 확대하지 않습니다.
