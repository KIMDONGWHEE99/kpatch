# Soulash 2 REA 활용 효과와 비용 평가

작성일: 2026-10-31 · 대상: Soulash 2 한국어 패치 1.0.0 및 다음 패치의 도구 선택

**REA는 Soulash 2의 실행 파일 안에 있는 표시 문구와 저장·외부 연동 동작을 확인하는 데 유용했습니다. 그러나 이번처럼 광범위한 조사와 도구 보완을 계속하는 방식이, 투입한 시간과 토큰에 걸맞은 최종 결과를 만들었다고 보기는 어렵습니다. 다음 패치에서는 REA를 필요한 코드 문제에 한정해 사용하는 것을 권고합니다.**

현재 근거로 내릴 수 있는 판단은 다음과 같습니다.

- **필요한 네이티브 코드 조사에는 가치가 있었습니다.** 번역 자료만 고쳐서는 해결하기 어려운 직접 표시 문구와 `None`·종족 이름 출력을 수정할 근거를 확보했습니다.
- **대부분의 번역 성과를 REA의 성과로 계산할 수는 없습니다.** JSON·TXT 번역, 글꼴 제작, 화면 확인, 차이 패치 생성은 별도 도구와 작업으로 이루어졌습니다.
- **이번 운영 방식은 비용 관리가 부족했습니다.** 큰 조사 목록과 반복 분석에 투입한 노력에 비해 최종 수정본의 화면·저장 호환성·설치 복구 확인이 남았습니다. 이는 도구 선택뿐 아니라 작업 우선순위의 문제입니다.
- **정확한 추가 비용과 투자 대비 수익률은 계산할 수 없습니다.** 같은 게임을 REA 없이 제작한 비교 실험이 없고, 전체 작업을 동일한 방식으로 계량한 기록도 없습니다. 다만 실제로 얻은 결과와 확인된 비용을 비교해 다음 방식은 정할 수 있습니다.

## 1. 이전 패치와 무엇이 달랐는가

## 2. REA가 실제로 기여한 부분

| 결과 | 사용자에게 의미 있는 차이 | REA의 기여와 한계 |
|---|---|---|

| 실제 저장 경로와 외부 연동 확인 | QA가 사용자 저장·설정·Steam 동작에 미치는 영향을 분리할 근거 확보 | 실제 저장 인자가 `WizardsOfTheCode/Soulash2`임을 확인. 이후 격리 변경과 실행 전후 비교가 있어야 안전성이 확인됨 |

구체적으로 `Default`는 화면 문구와 글꼴 식별자에 함께 쓰였습니다. 참조를 확인해 화면에 표시하는 지점만 바꾼 것은 단순 문자열 전체 치환보다 유의미한 개선입니다. 반면 직업 `None`과 종족 이름 문제는 실제 화면에서 발견한 뒤 REA/Ghidra로 수정 위치를 찾았습니다. 발견과 해결 과정에서 화면 검수와 코드 분석이 각각 기여한 것입니다. 이 효과는 단순히 “15곳을 고쳤다”는 수량만으로 평가할 수 없습니다. 저장 경계나 공통 출력 함수를 잘못 바꾸면 여러 화면과 저장에 영향을 줄 수 있기 때문입니다. 반대로 전체 번역 31,989위치, 한글 글꼴 3종, 패치 복원 검사 전체를 REA가 만들어 낸 성과로 계산하는 것도 과장입니다.

**이번에 입증된 것은 REA를 통한 조사 경로가 유용했다는 점입니다. REA가 없었다면 해결할 수 없었다거나, Ghidra를 직접 사용하는 것보다 빨랐다는 점은 입증되지 않았습니다.**

## 3. 시간과 토큰은 얼마나 확인되는가

### 보존된 REA 호출 시간

서버 로그 5개에서 호출 165회와 실행시간 합계 **35분 26.90초**를 확인했습니다. 서버 상태가 정상 반환인 호출은 164회, 오류 상태는 1회입니다. 정상 반환은 질문에 충분한 답을 얻었다는 뜻까지 보장하지 않습니다.

100초를 넘는 긴 호출 6개는 합계 **33분 4.92초**로, 관측된 호출 시간의 약 **93.3%**를 차지했습니다. 이 중 첫 실패는 Ghidra의 불러오기·분석 시작 제한 330초를 넘긴 경우였습니다. 이후 도구의 시작 제한을 30분으로 늘렸고, 뒤의 재개에서도 약 5분대의 긴 호출이 반복됐습니다. 실제 제한을 30분으로 설정한 것과 매번 30분을 사용한 것은 다릅니다.

이 값은 **도구 호출별 시간의 합계**입니다. 설치·설정, 결과를 읽고 판단한 시간, 번역·검수, 대기와 중단을 포함한 전체 작업시간이 아닙니다. 기록에 없는 설정 실패까지 “한 번뿐”이라고 판단하지도 않습니다. [비용 집계와 원본 로그 연결](../working_private/SOULASH_2/rea_value_review_20261031/cost_evidence.json), [시작 제한 변경](../tools/soulash2_rea_session.py)

반복 준비 비용에는 도구의 세션 정책도 관련됩니다. 당시 응답에는 종료 시 임시 분석 프로젝트를 지우고, 취소 후 다음 요청에서 원본을 재분석한다는 제한이 있습니다. 따라서 단순히 이전 결과를 잊어서 생긴 반복으로만 볼 수는 없습니다. 별도로 일괄 함수 분석 요청의 입력 형식 오류와 이를 처리하는 세션 도구 보완도 있었습니다. [당시 세션 제한](../working_private/SOULASH_2/rea/responses/xrefs_pref_org_r2.json), [입력 형식 오류](../working_private/SOULASH_2/rea/responses/resume2_pseudo_native_ui_batch.json)

### 보존된 토큰 사용량

Soulash 2 관련 부모 세션 3개와 자식 세션 9개의 기록을 확인했습니다. 이번 보고서 작성 비용을 제외하기 위해 **한국 시간 2026-10-31 06:45 이전**으로 구간을 제한하고, 세션별 마지막 누적값을 한 번씩만 합산했습니다.

| 기록 항목 | 관측된 카운터 참고합 |
|---|---:|
| 입력 토큰 | 352,916,101 |
| 입력 중 캐시 재사용 | 347,965,056 |
| 캐시가 아닌 입력 | 4,951,045 |
| 출력 토큰 | 1,442,310 |
| 입력과 출력 합계 | **354,358,411** |
| 입력 중 캐시 비율 | **98.60%** |

캐시란 앞서 처리한 입력을 재사용한 것으로 기록된 부분입니다. 캐시 토큰은 입력 토큰에 이미 포함돼 있습니다. 추론 출력 315,704개도 출력에 포함되므로 다시 더하지 않았습니다. 동일 누적값 반복 36회는 중복 합산하지 않았고, 12개 세션 모두 첫 누적값과 이후 증가량을 점검했을 때 부모 누적값 승계나 이중집계의 징후는 없었습니다.

**이 약 3억 5,436만이라는 숫자는 실제 청구량·요금·REA만의 비용이 아닙니다.** 현재 부모 세션은 한국 시간 10월 31일 01:25:02 이후에도 작업이 이어졌지만, 해당 구간의 사용량 기록이 연결되지 않습니다. 따라서 완전한 총사용량이나 확정된 하한으로도 제시하지 않습니다. 관련 세션에는 번역·도구 설정·분류·글꼴·검수가 섞여 있어 업무별 비용을 정확히 나눌 수 없습니다. 이전 게임에도 같은 기준의 전체 집계를 수행하지 않았으므로 “REA 때문에 토큰이 몇 배 증가했다”는 수치는 산출하지 않았습니다. [집계 방법·세션별 수치·한계](../working_private/SOULASH_2/rea_value_review_20261031/cost_evidence.json)

기록은 많은 입력을 반복 처리한 작업 형태와 부합합니다. 그러나 캐시 비율만으로 불필요한 반복의 양을 계산할 수는 없습니다. 또한 Ghidra가 5분 기다리게 했다고 그 5분 내내 모델 토큰이 소비됐다고 계산해서는 안 됩니다. 기다린 시간과 결과 해석·후속 호출에 사용한 토큰은 별개입니다.

## 6. 다음 패치에서는 어떻게 사용할 것인가

아래는 이번 평가에 따른 운영 제안입니다. 이 보고서 작성만으로 공통 도구나 프로젝트 지침의 구현 상태를 변경하지 않았습니다.

1. **기존 번역 파일과 엔진 도구부터 확인합니다.** JSON·CSV·Unity 자산·복원 가능한 스크립트로 해결되는지 먼저 판단합니다. 곧바로 전체 실행 파일 분석을 시작하지 않습니다.
2. **REA에 맡길 질문을 구체적으로 적습니다.** 예를 들어 “직업 `None`이 화면에 나오는 함수는 어디인가”, “이 이름이 저장에도 쓰이는가”, “실제 저장 경로는 어디인가”처럼 답을 얻으면 어떤 수정이 가능한지 명시합니다.
3. **한 번 준비한 분석을 재사용합니다.** 같은 실행 파일 지문·분석 설정이면 열린 세션이나 보존된 분석 응답을 우선합니다. 종료 뒤 분석 데이터베이스를 다시 쓸 수 있는지는 도구의 지원 범위를 먼저 확인합니다. 실패 후에는 원인이 달라진 재시도만 하고, 같은 조건의 시작·전체 분석을 반복하지 않습니다.
4. **반복 구조는 프로그램으로 검사합니다.** 같은 필드·소비 코드·원본 지문에 연결되는 규칙으로 대량 항목을 판정하되, 각 위치와 근거는 보존합니다. 모델에는 요약·차이·미해결 예시만 전달하고 거대한 원시 목록을 반복해서 읽히지 않습니다.
5. **대량 번역 전에 위험한 경계를 시험합니다.** 짧은 한국어 표시, 숫자·줄높이, 저장 후 불러오기, 식별자와 표시 이름 분리를 먼저 확인합니다. 특히 저장키 오류는 전체 번역 후 발견하는 것보다 일찍 확인하는 편이 유리합니다.
6. **시간·토큰을 작업 종류별로 기록합니다.** 환경 준비, REA 질의, 번역, 글꼴, 화면 검수, 패키징을 나누고 부모·자식 세션의 입력·캐시·출력을 중복 없이 집계합니다. 병렬 실행시간의 합과 실제 경과시간도 구분합니다.
7. **분석의 계속 여부를 중간에 판단합니다.** 초기 제안은 질문 하나에 20분 또는 연속 두 차례의 유효한 근거 미확보를 재평가 시점으로 삼는 것입니다. 자동 포기 기준이 아니라 질문을 좁히거나 대체 도구로 전환할 시점입니다. 해결되지 않은 항목은 그대로 남기며 완료로 처리하지 않습니다.
8. **최종 확인 시간을 먼저 확보합니다.** 대표 본편 화면, 저장·불러오기, 마지막 수정본, 최종 설치·복구 확인을 일정 끝에 밀어 두지 않습니다. 사전에 잡은 검수 예산을 소모할 만큼 조사를 확대하려면, 늘어나는 범위와 얻을 결과를 먼저 비교합니다.

다음 작업에서 REA의 가치는 호출 수나 추출량이 아니라 **해결한 사용자 문제, 보존한 게임 동작, 줄어든 재작업, 최종 검수까지 마친 범위**로 평가해야 합니다. 정확한 효과를 측정하려면 같은 문제에 대해 기존 도구로 확인하는 단계와 REA를 추가하는 단계를 나누고, 각 단계에서 새로 얻은 근거와 사용량을 기록하는 방식이 적절합니다.
