## 1. 최종 결론

이번 작업은 최초 접근만으로 한글화가 완성되지 않았고, 사용자가 여러 차례 실제 플레이 화면을 제보한 뒤에야 번역 범위가 확장되었습니다. 가장 큰 문제는 초기에 게임의 영어 문구가 일반 Localization StringTable에 주로 들어 있을 것이라고 가정한 점입니다. 실제로는 시작 화면 직접 텍스트, 여러 공유 자산의 글꼴, 장면별 직렬화 문구, 공용 `resources.assets`, IL2CPP 실행 코드 문자열, enum 이름, 이미지·영상 속 녹화 화면까지 여러 계층에 분산되어 있었습니다.

최종 v0.5.1에서는 제보 화면만 고치는 반응식 작업을 중단하고 정적 전수 조사 방식으로 전환했습니다. 화면 텍스트 자산 1,638행을 감사하고, 실행 코드의 표시 문자열 260개를 치환했으며, 장면 7개와 공용 자산을 다시 추출해 의도한 번역값의 누락 0건과 대상 원문 잔존 0건을 확인했습니다. 성장 트리 분류 이름은 문자열이 아니라 enum 이름을 `ToString()`으로 출력하는 구조여서 메타데이터 필드까지 수정했습니다.

다만 실제 게임을 자동 실행해 전 구간을 육안 검수한 것은 아닙니다. 따라서 결과는 `텍스트 레이어 정적 전수 한글화`로 정의합니다. 튜토리얼 예시 사진·녹화 영상에 촬영 당시 픽셀로 박힌 작은 영문 HUD, 고유 로고, 제작자 이름, 버전 번호와 역 코드는 유지됩니다.

## 3. 기존 방식의 문제점

### 3.1 문자열 출처를 너무 일찍 한정함

초기에는 공식 Localization StringTable이 핵심이라고 판단했습니다. 하지만 이 게임은 표시 문구를 다음 위치에 나누어 저장했습니다.

- Addressables Localization StringTable
- `level0`~`level6`의 TMP/Text 직접 값
- `resources.assets`, `sharedassets0.assets`의 MonoBehaviour·ScriptableObject 필드
- `global-metadata.dat`의 IL2CPP 문자열 리터럴
- enum 필드 이름을 `ToString()`으로 표시하는 성장 트리 분류
- 튜토리얼 이미지·영상에 픽셀로 포함된 녹화 화면

문자열 출처 목록을 작업 초기에 확정하지 않았기 때문에 한 계층을 고칠 때마다 다른 계층의 누락이 드러났습니다.

### 3.2 글꼴 조사를 일부 자산에만 수행함

처음 교체한 글꼴만으로 충분하다고 보았지만, 시작 화면과 게임 화면이 서로 다른 공유 자산의 SDF 글꼴을 사용했습니다. 결과적으로 번역 문자열 자체는 존재해도 한글이 네모로 출력되었습니다. 글꼴은 파일 이름이 아니라 실제 참조 관계와 모든 사용 자산을 기준으로 조사해야 했습니다.

### 3.3 사용자 화면 제보에 과도하게 의존함

사용자가 보여 준 화면은 문제를 확인하는 데 매우 유용했지만, 이를 누락 탐색의 주된 방법으로 사용한 것은 잘못이었습니다. 게임을 10분만 해도 새로운 영어가 계속 나타났고, 사용자가 모든 분기와 후반 콘텐츠를 방문해야 하는 부담이 생겼습니다. 정적 전수 검사를 먼저 하고 플레이 제보는 배치·잘림·런타임 조건 확인에만 사용했어야 합니다.

### 3.4 완료 판단 기준이 불명확함

`패치 파일이 정상 생성됨`, `번역값이 일부 화면에 표시됨`, `전체 사용자 노출 문자열이 분류됨`은 서로 다른 상태입니다. 초기에는 첫 두 상태를 지나치게 완성에 가깝게 표현했습니다. 앞으로는 `UNKNOWN 0건`, `번역 대상 원문 잔존 0건`, `정적 구조 검증 통과`, `실행 QA 상태 명시`를 별도 게이트로 관리해야 합니다.

### 3.5 설치 경로를 개인 환경에 맞춤

최초 설치기는 현재 PC의 D 드라이브 경로를 기본값으로 사용했습니다. 명령줄에서 다른 경로를 지정할 수는 있었지만 일반 사용자에게 적합하지 않았습니다. 배포판이라면 처음부터 Steam 라이브러리 자동 탐색, 다중 설치 선택, 직접 입력, 제거·검증 도구의 동일 경로 처리까지 포함했어야 합니다.

## 7. 다음 프로젝트부터 적용할 개선 절차

### 단계 A: 기준선과 출처 지도 작성

1. 원본 파일 해시와 게임 빌드를 기록합니다.
2. StringTable, 장면 텍스트, 공용 자산, 코드 문자열, enum, 미디어를 모두 목록화합니다.
3. 각 문자열에 출처 파일, 개체, 필드, 코드 참조 메서드를 연결합니다.

### 단계 B: 분류 완료 후 번역

모든 문자열을 다음 중 하나로 분류합니다.

- `VISIBLE_TRANSLATE`: 사용자가 읽는 번역 대상
- `VISIBLE_KEEP`: 고유명사·버전·코드 등 유지 대상
- `INTERNAL`: 경로·오브젝트 이름·로그·식별자
- `MEDIA`: 이미지·영상 픽셀 문구
- `UNKNOWN`: 추가 확인 필요

`UNKNOWN`이 남아 있는 상태에서는 완성판을 만들지 않습니다.

### 단계 C: 글꼴과 레이아웃을 말뭉치 기준으로 검증

전체 번역에서 필요한 문자를 계산하고 실제로 참조되는 모든 TTF/SDF 글꼴을 검사합니다. 누락 글리프 0건을 확인한 뒤 좁은 버튼, 여러 줄 팝업, 숫자와 아이콘이 섞인 문구를 별도 점검합니다.

### 단계 D: 재추출과 구조 검증

수정 후보를 다시 읽어 번역값 존재, 원문 제거, 토큰·태그 보존을 기계적으로 확인합니다. IL2CPP 메타데이터는 별도 파서와 Cpp2IL 양쪽에서 검증합니다.

### 단계 E: 실행 검수 상태를 분리

정적 검증, 자동 실행 스모크 테스트, 실제 전 구간 육안 검수를 서로 다른 상태로 기록합니다. 수행하지 않은 항목은 `NOT_RUN`으로 남기며 추정으로 통과 처리하지 않습니다.

## 8. 최종 평가

사용자의 반복 피드백은 단순한 추가 요청이 아니라 초기 작업 방식의 결함을 드러냈습니다. 특히 “사용자가 모든 부분을 직접 플레이할 수 없다”는 지적이 핵심이었습니다. 한글화 도구의 역할은 사용자가 누락을 찾아 주기를 기다리는 것이 아니라, 먼저 게임의 문자열 구조를 최대한 완전하게 조사하고 남은 불확실성만 명확히 제시하는 것입니다.

이번 작업은 여러 차례 수정 끝에 정적 전수 방식으로 전환되었지만, 다음 작업부터는 이 방식이 최초 단계가 되어야 합니다.
