# 한글패치 제작 핵심 지침서

문서 버전: 1.3 · 최초 적용: 2026-09-05 · 개정: 2026-11-17 · 대상: 신규 제작, 수정판, 게임 업데이트 대응

**사용자에게 누락 탐색과 반복 플레이를 맡기지 않는다. 제작자가 전수 조사와 실행 검수를 수행하고, 확인한 후보와 같은 파일을 배포한다.** 내부 시행착오는 허용하되 같은 결함을 다음 작업에 넘기지 않는다.

이 문서는 공통 절차의 기준이다. [AGENTS.md](../AGENTS.md)는 작업자가 항상 지킬 요약, [런타임 QA 참조](KOREAN_PATCH_RUNTIME_QA_REFERENCE.md)는 글꼴·실행·저장 격리의 상세 근거다. 게임별 명세에는 공통 규칙을 복사하지 않고 해당 게임의 값과 예외만 기록한다. 사용자의 현재 요청과 이미 허용한 범위를 우선하며, 옛 템플릿의 추가 승인 절차를 자동 적용하지 않는다.

## 1. 시작과 재개: 다음 미완료 단계부터 진행한다

1. [현재 상태](../PROJECT_STATUS.md)와 해당 게임의 README·TASK_SPEC을 읽는다. 신규 게임이면 [작업 명세](../tasks/TASK_SPEC_TEMPLATE.md)와 [게임 설정 양식](../templates/GAME_CONFIG_TEMPLATE.yaml)을 채운다. 허용된 조사·작업의 명세는 제작자가 작성하며 사용자에게 대신 작성하라고 요구하지 않는다.
2. 새 한글화 작업에서는 런타임 QA 참조를 읽고 G3·G5 계획에 반영한다. 재개할 때는 변경된 지침과 해당 작업 증거를 우선 읽는다.
3. 입력 해시, 직전 후보, 검증 도구 버전, 미해결 문제를 확인한다. 옛 `PASS` 문구만 믿고 다음 단계로 넘어가지 않는다.
4. 다음 표에서 증거가 없는 가장 이른 필수 단계를 선택한다. 실패와 관계없는 조사·문서화는 계속할 수 있지만 실패한 결과를 하위 단계의 통과 입력으로 쓰지 않는다.
5. 게임 폴더·빌드가 불명확하면 우선 읽기 전용 탐색으로 확인한다. 도구로 확인할 수 없는 필수 정보만 간결하게 질문한다. 일반 번역 표현, 파일 이름, 도구 선택 등 되돌릴 수 있는 선택 때문에 작업을 멈추지 않는다.
6. 작업은 현재 대화에서 시작한다. 파일·엔진 도구로 해결되지 않는 코드 질문이 생겼을 때 연결된 REA 도구를 직접 호출한다. REA 전용 PowerShell 실행기·새 서버·전체 코드 분석을 시작의 필수 조건으로 삼지 않는다. 직접 연결과 필요한 분석 엔진의 준비 여부는 별개이며 [현재 대화에서 REA 사용](REA_IN_CHAT_WORKFLOW.md)을 따른다.

현재 자동화 수준은 [개선 작업 목록](PROCESS_IMPROVEMENT_BACKLOG.md)에 별도로 기록한다. 이 지침서의 존재는 검증 프로그램 구현 완료를 뜻하지 않는다. 기존 도구의 허점이 관련된 단계는 독립 검사로 동등한 증거를 확보하거나 `BLOCKED`로 남긴다.

2026-11-04 사용자 지정 후속 작업: **다음 신규 게임에서 문구별 자동 재적용 방식을 한 번 시험한다.** 기존과 일치하는 문구는 한국어로 재적용하고, 새로 생기거나 변경된 문구는 영어로 유지하는 것을 허용한다. 게임 구조에 맞는 방식과 실제 실행 경로를 명세에 포함하고 [PROC-09의 시험 범위](PROCESS_IMPROVEMENT_BACKLOG.md)를 따른다. 아직 미구현이며 모든 미래 업데이트의 호환성이나 전체 번역 완료를 보장하는 규칙은 아니다.

## 2. 필수 단계와 완료 조건

게이트는 다음 단계로 진행하기 위한 검사다. G0~G8은 새 완성판의 공통 식별자이며, 상태·명세·보고서에서 같은 이름을 쓴다.

| ID | 단계 | 최소 산출물 | 통과 조건 |
|---|---|---|---|
| G0 | 기준선·환경 고정 | 원본 파일 목록, 도구 버전·해시, 작업·저장 경계 | 빌드·파일 크기·SHA-256(내용 지문) 확인, 독립 작업 사본 확보 |
| G1 | 기술 위험 선검증 | 변경 없는 추출·재저장 결과, 소규모 글꼴·로딩 시험 | 구조·참조 보존, 사용 가능한 수정·복구 경로 입증 |
| G2 | 출처 전수 조사·분류 | 위치별 목록, 추출 오류 대장, 미디어 판정 | 조사 범위 누락·미해결 추출 오류·근거 없는 판정·`UNKNOWN` 각 0 |
| G3 | 문맥 번역·글꼴 준비 | 공식 번역 원본, 용어집, 필요 문자·글꼴 의존 관계 | 대상 전부 번역·교정, 제어 정보 보존, 실제 사용 글꼴의 출력 조건 충족 |
| G4 | 후보 정적 검증 | 후보 재추출, 위치별 비교, 구조·메타데이터·카탈로그 검사 | 잘못된 위치·빈 번역·원문 잔존·예상 밖 변경·태그 구조 오류 각 0 |
| G5 | 제작자 그래픽 검수 | 실행 기록, 화면별 결과, 로그, 저장 전후 비교 | 필수 화면 검사 완료, 실제 후보 경로 확인, 글리프·패치 고유 로딩 오류 0, 사용자 저장 무변경 |
| G6 | 후보 고정·차이 패치 | 후보·패키지 파일 목록, 정방향·역방향 복원 증거 | 모든 패치가 기대 파일로 복원, 허용된 배포 파일만 포함 |
| G7 | 최종 ZIP 설치·복구 | 최종 ZIP 해시, 그 ZIP에서 꺼낸 설치기의 시험 기록 | 설치·제거·업데이트 거부·중단 복구·경로 시험 통과, 최종 게임 파일 해시 일치 |
| G8 | 배포 판정·인수인계 | 최종 외부 검증 보고서, 유지 문구·검수 범위·복구 안내 | 같은 빌드의 유효한 필수 증거 완비, 미해결 차단 항목 0 |

G1의 소규모 시험은 대량 번역 전에 글꼴·재저장·목록 로딩 실패를 찾기 위한 것이다. G3 전체 문자 검사나 G5 그래픽 검수를 대신하지 않는다. 초기 화면 진입 시험에도 G5의 저장 격리·실제 경로 확인을 적용한다.

문서 수정만 하는 작업에는 게임 실행 게이트를 요구하지 않는다. 링크·상태·양식 일관성을 확인하고 게임 검증은 이번 작업 범위 밖이라고 기록한다. 게임 패치의 필수 검증을 문서 작업의 통과 결과로 승격하지 않는다.

## 3. 상태와 증거: 완료 여부를 추정하지 않는다

| 상태 | 의미 | 배포 판정 |
|---|---|---|
| `NOT_RUN` | 아직 실행하지 않음 | 필수 항목이면 차단 |
| `PASS` | 해당 입력과 범위에 대한 유효한 증거가 있음 | 해당 항목만 충족 |
| `FAIL` | 검사를 실행했고 결함을 발견함 | 차단 |
| `BLOCKED` | 필요한 입력·접근·도구가 없어 실행할 수 없음 | 차단; 막힌 부분과 필요한 조치를 기록 |
| `STALE` | 입력·도구·판정 기준이 바뀌어 옛 증거가 만료됨 | 재검증 전 차단 |
| `NOT_APPLICABLE` | 해당 기능·변경·지원 범위가 존재하지 않음 | 구체적인 근거가 있을 때만 제외 |

문서의 `BLOCKED`는 개별 검사 상태다. 자동 실행 시스템이나 대화 작업의 상태를 변경하라는 명령이 아니다.

- 기능이 없어서 해당하지 않는 경우와 아직 화면에 도달하지 못한 경우를 구분한다. 접근 실패는 `NOT_APPLICABLE`이 아니다.
- G0, G2, G3, G4, G5, G6, G7, G8 전체를 제외하지 않는다. 예컨대 Mono 게임의 IL2CPP 분석, 최초 공개판의 이전 공개 패치 갱신 같은 세부 검사만 제외할 수 있다. G1도 변경 포맷의 근거 없이 생략하지 않는다.
- 같은 해시의 중복 이미지·문구는 검토를 공유할 수 있지만 모든 사용 위치와 화면 문맥은 목록에 남긴다.
- 모든 검증은 `game_id`, `build_id`, 검사 ID, 실제 명령·도구 버전, 시작·종료 시각, 종료 코드, 입력·출력 해시, 검사 개수, 실패 목록, 증거 경로를 기록한다. 개인 경로와 저장 원문은 비공개 증거에 둔다.
- 자동 검사와 제작자의 육안 검사를 구분한다. 육안 검사는 화면·영역·관찰 결과와 해당 이미지 해시를 기록한다. 파일이 있다는 사실만으로 육안 검사 `PASS`를 만들지 않는다.
- 전체 단계는 필수 세부 결과를 집계해 판정한다. 필수 결과의 누락, 중복 ID, 알 수 없는 상태, 서로 다른 빌드의 혼합도 실패로 처리한다.
- `build_id`는 사람이 붙이는 고유 이름이고 무결성 증명은 아니다. 입력 목록 자체의 해시와 실제 파일 해시를 함께 검증한다. 같은 ID의 후보를 덮어쓰지 않는다.

자료 형식은 [검증 기록 양식](../templates/QA_LEDGER_TEMPLATE.yaml), 사람에게 전달할 결과는 [결과 보고 양식](../templates/RESULT_REPORT_TEMPLATE.md)을 사용한다. 두 양식의 경로는 기록 계약이며 아직 존재하지 않는 자동 실행 명령을 뜻하지 않는다.

## 4. G0~G1: 대량 작업 전에 실패 원인을 줄인다

- 게임 빌드 번호, 플랫폼, 엔진 버전, Unity의 Mono/IL2CPP, Addressables/YooAsset 사용 여부를 확인한다. 다른 엔진이면 해당되는 저장·로딩 체계를 기록한다. 모르는 값은 추정값과 근거를 구분한다.
- 원본의 전체 대상 파일 목록·크기·해시를 먼저 고정한다. 파일 추가·삭제, 업데이트, 다른 모드가 확인되면 기존 패치를 강제 적용하지 않는다. 새 기준선 조사로 전환한다.
- Python·라이브러리·재패킹·메타데이터 분석·xdelta·글꼴 버전과 출처·라이선스·파일 해시를 기록한다. 로컬에 있다는 이유로 버전 고정이 끝났다고 보지 않는다.
- 보호된 작업 사본에서 변경 없이 추출·재저장한다. 바이트가 달라지면 구조·내용·참조 비교와 로딩 증거로 이유를 설명한다. 알 수 없는 차이를 허용하지 않는다.
- 새로 수정할 자산 형식마다 소규모 한국어·태그·아이콘·조합 문구를 넣어 재열기와 로딩을 시험한다. 검수용 변경은 별도 사본에만 둔다.
- 대량 번역 전에 숫자·줄높이와 표시 이름/내부 식별자의 경계를 확인하고, 격리 사본에서 저장 후 불러오기를 시험한다. 저장·직렬화에 쓰이는 이름은 유지하고 표시 계층에서 변환한다. 소규모 시험은 전체 번역·전체 분기 검증을 대신하지 않는다.
- [폴더·데이터 경계](../ARCHITECTURE_SPEC.md)에 따라 경로를 정한다. 재패킹 시험 자산·게임 DLL·역분석 결과도 비공개 영역에서 다룬다.

## 5. G2: 조사 목록의 빈틈을 닫는다

먼저 조사할 파일·묶음·객체·코드·미디어의 전체 목록과 제외 근거를 만든다. 읽을 수 있었던 문자열 수만으로 전수 조사를 주장하지 않는다. 파일을 읽지 못하거나 객체 해석이 실패하면 오류 대장에 원본 해시·객체 위치·실패 단계·대체 조사 증거를 남긴다.

필수 계층은 다음과 같다. 해당 엔진에 이름이 다르면 대응 출처를 기록한다.

1. Localization StringTable과 언어 슬롯.
2. 장면·프리팹의 TMP/Text 직접 문구.
3. `resources.assets`, `sharedassets*.assets` 등의 MonoBehaviour·ScriptableObject 표시 필드와 TextAsset.
4. Mono 코드 문자열 또는 IL2CPP `global-metadata.dat` 문자열, 실제 사용 메서드·화면 연결.
5. `ToString()`으로 표시하는 enum(열거형) 이름.
6. 실행 중 조합되는 문장·숫자·단위·서식·조사.
7. 개발·예비·접근성·도움말·오류 화면의 실제 표시 필드.
8. 이미지·스프라이트·동영상 픽셀 문구. 게임 안 표시물과 외부 서비스 화면을 구분한다.

| 분류 | 판정 조건 |
|---|---|
| `VISIBLE_TRANSLATE` | 화면에 표시되고 한국어로 바꿀 항목. 기대 번역과 사용 위치를 연결 |
| `VISIBLE_KEEP` | 유지할 이유가 확인된 고유명사·코드 등. 범위와 사유를 기록 |
| `INTERNAL` | 표시되지 않는 키·경로·로그 등임을 사용 참조나 구조로 확인 |
| `MEDIA` | 픽셀 자료. 별도로 `TRANSLATE`, `KEEP`, `NO_TEXT`, `UNKNOWN` 처리와 근거를 기록 |
| `UNKNOWN` | 표시 여부·처리·추출 결과를 확정하지 못한 항목. 새 항목의 기본값 |

**번역 목록에 없다는 이유, 클래스·파일 이름이 낯설다는 이유, 영어가 짧다는 이유로 내부용 처리하지 않는다.** 기존 `UNKNOWN`을 일괄 유지 대상으로 바꾸지 않는다. `MEDIA`라는 분류만으로 검수 완료가 되지 않으며 미디어 처리의 `UNKNOWN`도 최종 0건에 포함한다.

위치 ID는 기준선 안에서 유일해야 한다. 자산은 파일·내부 자산·객체 ID·필드 경로, 코드는 어셈블리·메서드·문자열 위치, 미디어는 자산·변형·영역·프레임 구간을 사용한다. 원문 해시와 판정 근거를 붙인다. 원문이 같아도 메뉴 명령과 설명문처럼 문맥이 다르면 번역을 분리한다.

미디어는 원본 해시가 같은 경우만 검토를 공유한다. 검수 이미지·영상 프레임과 실제 포함 자산을 대조한다. 접촉 시트(작은 이미지를 모은 검수판) 개수를 코드에 고정하지 않는다. 작은 글자·영상 구간은 확대·프레임 확인하고, 글자 인식 도구의 미검출을 `NO_TEXT` 근거로 단독 사용하지 않는다.

## 6. G3~G4: 정확한 번역을 정확한 위치에서 검증한다

- 공식 번역 원본을 하나 정한다. 빌드용 파일은 여기에서 생성한다. 수정은 원본에서 시작하며 결과 파일에만 임시로 번역을 덧붙이지 않는다.
- 화자·문맥·기능·길이 제약·용어집을 붙여 번역한다. 숫자, 부정문, 조건, 단위, 선택지의 의미를 별도 교정 단계에서 확인한다. 자동 용어 검사와 사람이 읽는 문맥 검사를 구분한다.
- 토큰·아이콘 속성·자리표시자 형식·제어 줄바꿈을 보존한다. 쌍 태그의 열고 닫는 순서와 중첩, 단독 태그, 이스케이프를 검사한다. 개수 비교만으로 통과시키지 않는다. 어순에 따른 자리표시자 이동은 허용하되 이름·형식·개수는 보존한다.
- 조합 문구는 실제 서식 처리 방식으로 빈 값·최솟값·일반값·큰 수·긴 이름을 넣어 확인한다. 런타임에서 쓰는 문자까지 전체 필요 문자 집합에 포함한다.
- 텍스트 → 실제 글꼴 → 원본 Font → 아틀라스(글자 이미지) → 재질 → 폴백(대체 글꼴)과 글꼴 전용 묶음을 끝까지 추적한다. 정적 문자표·글리프표 또는 동적 생성·Source Font·다중 아틀라스 조건을 각각 확인한다. 순환·누락 참조와 재질 불일치를 허용하지 않는다.
- 후보를 다시 추출해 **위치마다 기대 번역과 실제 값이 정확히 같은지** 비교한다. 빈 값, 잘못된 한국어, 위치 교환, 객체·파일 삭제, 예상 횟수 차이도 검출한다. 원문이 사라졌다는 사실만으로 완료 처리하지 않는다.
- 허용된 객체·필드·메서드 밖의 변경, ID·순서·참조 손상을 검사한다. 빌드 코드의 치환 성공 카운터를 독립 검증으로 재사용하지 않는다.
- IL2CPP 메타데이터를 바꾸면 Cpp2IL 또는 동급 도구로 다시 분석한다. 변경 묶음의 크기·CRC·해시 정책을 원래 로딩 방식에 맞춰 갱신하고 목록을 다시 연다.

검사기 자체도 알려진 결함을 잡아야 한다. 합성 자료에서 미검토 문구·추출 실패·미검토 이미지, 빈 번역·위치 교환, 깨진 태그, 글꼴 누락, 만료된 증거가 통과하지 않는지 확인한다. 정상 입력도 함께 통과해야 하며 항상 실패하는 검사기를 완성으로 보지 않는다.

## 7. G5: 사용자 플레이를 제작자 검수로 대체한다

**화면을 조작하지 않고 검수한다.** 컴퓨터 유즈, 마우스·키보드 입력 주입, 창을 앞으로 가져오는 동작을 쓰지 않는다. 사용자가 같은 PC를 쓰고 있다고 가정한다. 게임 안에 넣은 검수 코드가 요청 파일을 읽어 화면을 옮기고 게임 화면을 PNG로 직접 저장하게 하며, 창은 포커스를 가져가지 않게 띄우고 소리를 끈다. 최소화하면 화면 갱신이 멈출 수 있으므로 최소화하지 않는다. 참고 구현은 Godot의 `tasks/HOW_EMPIRES_WORK/tools/qa_driver.gd`와 `launch_qa.py`, Unity의 `tasks/KINGDOM_INC_DEMO/tools/KoreanQA/Driver.cs`다. 내부 검수 코드를 넣을 수 없는 게임은 이유를 기록하고, 사용자와 시간을 정해 사용자가 화면을 조작하고 제작자가 캡처·판독하는 방식으로 진행한다.

검수 계획은 번역이 끝나기 전에 만든다. 제작자가 화면별 테스트 저장 자료, 장면 진입, 대화 재생, 조건 설정을 준비한다. 접근 가능한 공식 기능과 최소한의 검수 전용 변경을 우선한다. 사용자의 저장 파일이나 업적·통계를 시험 재료로 사용하지 않는다.

실행 전에 저장 파일, 설정·레지스트리, 로그, Steam 사용자 데이터·클라우드 등 실제 쓰기 위치를 조사한다. 테스트 제품명 변경만으로 모든 저장·전송이 분리됐다고 가정하지 않는다. 분리할 수 없는 쓰기가 남으면 실행을 막고 대안을 마련한다. 저장 전후에는 파일 목록·크기·해시와 필요한 설정 값을 비교한다.

| 필수 화면군 | 검수 내용 |
|---|---|
| 로고·첫 화면·버전 | 한글 출력, 런타임 조합 문구, 시작 로딩 |
| 메뉴·설정·언어 | 버튼, 저장·재진입, 지원 언어 슬롯 전환, 해상도·글자 크기 |
| 새 게임·이어하기 | 최초 진입과 테스트 저장 로드 |
| HUD·알림·툴팁 | 숫자·단위·아이콘·긴 이름·좁은 영역 |
| 대화·선택지 | 화자, 긴 문장, 선택 후 결과, 분기 접근 |
| 일시정지·도움말·접근성 | 예비·오류 문구, 입력 안내, 표시 배율 |
| 사망·결과·종료 | 승패·완료·종료 확인 등 존재하는 각 흐름 |

해당 게임에 없는 화면만 구체적인 근거로 제외한다. 접근하지 못한 화면은 미검증으로 남기고 G5를 통과시키지 않는다. 전체 분기와 대표 화면 검증을 같은 것으로 표현하지 않는다.

1. 후보 해시와 검수 사본의 차이를 파일뿐 아니라 객체·필드·메서드 수준에서 확인한다. 분리 제품명·로그 위치·시험 조건 변경만 허용하고 배포본에 섞이지 않음을 확인한다.
2. 실제 그래픽 모드로 실행한다. 프로세스의 실제 실행 경로를 수집하며, Steam이 설치본을 다시 띄우면 후보 검수로 인정하지 않는다. 잘못된 실행을 중단하고 저장 영향을 확인한다.
3. 실행 ID, 프로세스 경로·번호, 시각, 장치·해상도, 후보 해시, 화면별 캡처·로그를 같은 기록에 묶는다. 경로·프로세스 번호를 보고서 코드에 상수로 넣지 않는다.
4. 실제 화면에서 네모 글자, 깨진 자모, 잘림·겹침, 태그 노출, 읽기 어려운 크기를 확인한다. 로그의 글리프 누락은 0건이어야 한다. 로딩·카탈로그 오류는 원본과 비교해 패치 고유 오류 0건을 확인한다.
5. 표시된 문자열·글꼴·화면을 전수 목록과 연결하고 아직 관찰하지 못한 항목을 별도 목록으로 만든다. 관찰 범위를 숫자와 분모로 보고하며 알 수 없는 분모를 100%로 쓰지 않는다.
6. 종료·저장 무결성·검수 전용 파일 정리를 확인한다. 저장 격리나 복원이 실패하면 화면이 정상이어도 통과시키지 않는다.

배치 모드·미리보기·캡처 존재 확인은 실제 화면 검수를 대체하지 않는다. 정상 진행을 건너뛴 검수는 도달한 화면 검증으로 기록하며 게임 규칙·분기 전체가 정상이라는 근거로 확대하지 않는다.

## 8. G6~G8: 검증한 파일을 그대로 배포한다

1. G4·G5를 통과한 후보의 전체 파일 목록과 해시를 고정한다. 이후 내용이 바뀌면 새 후보로 만들고 영향받는 검사를 다시 수행한다.
2. 차이 패치를 생성한 즉시 원본에서 후보로 복원하고 후보 해시를 확인한다. 제거용 패치도 후보에서 원본으로 복원해 원본 해시를 확인한다. 지원하는 이전 패치마다 같은 원칙을 적용한다.
3. 배포는 명시적인 파일 허용 목록을 사용한다. 설치·제거기, 필요한 차이 패치 도구와 라이선스, 문서, 차이 파일만 허용한다. 재구성 자산·게임 DLL·검수 코드·개인 경로·저장 원문을 넣지 않는다.
4. 설치기는 변경 파일과 빌드 식별에 필요한 무변경 파일을 확인한다. 미지원 해시·누락·손상·실행 중 게임을 거부하고 대상 파일을 바꾸지 않는다. 여러 Steam 라이브러리, 임의 경로·한글·공백, 경로 직접 지정도 지원 범위로 시험한다.
5. 모든 결과를 준비·검증한 뒤 교체한다. 대상 경로가 게임 폴더 안인지 확인하고 교체 직전 해시를 재확인한다. 중간 실패 시 이전 상태로 복구하며, 강제 종료 후에도 진행 기록을 바탕으로 복구할 수 있어야 한다.
6. **최종 ZIP을 먼저 고정한 뒤 그 ZIP을 별도 폴더에 풀어서** 설치·제거·중단 복구를 시험한다. ZIP 생성 전의 설치기 시험만으로 G7을 통과시키지 않는다.
7. 최종 검증 보고서는 ZIP 밖에서 ZIP 해시와 시험 증거를 참조한다. 아직 하지 않은 최종 ZIP 시험을 내부 보고서에 완료로 쓰지 않는다. 시험 후 문서·설치기·차이 파일을 바꾸어 ZIP을 다시 만들면 새 ZIP에 대해 G7을 다시 수행한다.
8. 최종 대상 파일 해시와 사용자에게 전달할 ZIP 해시를 확인한다. 배포 준비와 실제 공개·설치를 구분하고, 요청에서 허용된 작업은 계속 진행한다. 공개·설치가 요청 범위 밖이면 검토 가능한 산출물 준비를 끝낸 뒤 필요한 허용 범위만 확인한다.

설치 시험은 고정된 “12종” 숫자가 아니라 적용 가능한 아래 사례의 ID와 결과로 집계한다.

| 시험군 | 필수 사례 |
|---|---|
| 정상 흐름 | 원본 설치, 중복 설치, 제거, 중복 제거, 최종 해시 |
| 지원 상태 | 이전 공개 패치 갱신·원본 복구, 부분 설치 재개·제거 |
| 거부 | 다른 빌드, 변조·누락 파일, 손상된 차이 파일·도구, 잘못된 경로, 실행 중 게임 |
| 중간 실패 | 두 번째 교체 실패, 파일 잠금, 쓰기 실패, 강제 중단 후 복구; 사용자 저장 무변경 |
| 배포·경로 | 최종 ZIP 해시, 허용 목록, 원본 자산 미포함, 임의·한글·공백 경로, 추가 라이브러리 |

파일 쓰기 실패는 작은 격리 자료나 실패 주입으로 시험한다. 실제 디스크를 채우거나 사용자 파일의 권한을 바꾸지 않는다.

설치 시험은 게임 사본을 쌓아 두지 않는다. 2026-11-10 How Empires Work 설치 시험은 사례 30여 개마다 게임 전체를 복사해 남겨 39GB를 썼고 디스크 부족으로 한 차례 실패했다.

- 시험 전에 여유 공간을 확인한다. (게임 크기 × 3) + 20GB보다 적으면 먼저 정리한다.
- 사례 하나가 끝나면 시험 도구가 그 사례의 게임 사본을 바로 지운다. 결과는 사례 ID·판정·관련 해시·오류 메시지로 남긴다. 실패한 사례의 폴더만 원인 분석이 끝날 때까지 둔다.
- 사본에는 설치기가 확인하는 파일만 넣는다. 설치기가 전체 폴더를 요구하는 사례만 게임 전체를 복사한다.
- 정방향·역방향 복원으로 만든 파일은 해시를 기록한 직후 지운다.

## 9. 반복 작업을 줄이는 방법

### 9.1 도구 선택과 REA 사용 범위

- JSON·CSV·언어표·엔진 자산 도구·복원 가능한 코드를 우선한다. REA는 직접 표시 문구, 내부 값과 화면 출력의 경계, 실제 저장 경로, 글꼴 사용 함수 등 해결되지 않은 질문에 사용한다.
- 호출 전 대상 파일 지문, 질문, 필요한 답, 답에 따른 수정·검증을 짧게 연결한다. 확인된 위치에서 함수·참조를 좁힌다. 전체 함수 복원은 필요한 이유와 예상 산출물이 있을 때만 수행한다.
- 연결된 MCP 도구가 충분하면 이를 우선한다. 매 작업마다 설치·진단을 반복하거나 CLI 서버를 추가하지 않는다. 실제 누락·오류가 있을 때 해당 연결/엔진만 보완한다. 도구 목록에서 이름이 보이는 것, 상태 조회 성공, 심층 분석 성공을 구분한다.
- REA의 네이티브 실행 파일·DLL 코드 분석은 Ghidra를 기본으로 한다. `open_binary`에서 `provider_id: "ghidra"`를 명시하고 필요한 함수의 `analyze_function` 또는 `procedure_pseudo_code` 응답을 확인한다. 같은 입력의 유효한 기존 Ghidra 근거는 재사용한다. Ghidra 장애 시 원인과 복구·대체 경로를 기록하고 다른 분석기의 결과를 Ghidra 결과로 표시하지 않는다. JSON·엔진 자산·관리 코드에는 해당 형식 전용 도구를 우선한다. [대화 내 사용 절차](REA_IN_CHAT_WORKFLOW.md)를 따른다.
- 같은 파일 지문·제공자·분석 설정의 열린 세션과 보존 응답을 재사용한다. 지원되는 스냅샷을 저장할 수 있어도 모든 함수의 분석이나 재시작 비용이 없어졌다고 가정하지 않는다. 종료·취소 시 임시 분석이 사라질 수 있으므로 필요한 증거를 먼저 보존한다.
- 실패는 연결·입력 형식·분석 엔진·호출 시간 제한으로 구분한다. 같은 조건의 실패를 반복하지 않고 반환된 복구 안내와 현재 입력 형식을 따른다. 호스트 시간 초과는 분석 종료를 뜻하지 않으므로 중복 분석을 시작하지 않는다.
- 질문별 20분 경과 또는 연속 2회 유효한 근거 미확보 시 질문·범위·도구·재사용 자료를 재평가한다. 이는 자동 포기나 사용자 승인 절차가 아니다. 진행 중인 분석을 무조건 끊지 말고 결과·정리 상태를 확인하며, 허용된 독립 작업을 계속한다.

### 9.2 대량 처리와 비용 관리

- 반복 구조는 입증된 파일 형식·필드·사용 코드 규칙으로 프로그램에서 처리하고 각 위치의 지문·근거를 남긴다. 근거 없는 내부용 일괄 분류는 금지한다.
- 모델에는 질문에 필요한 요약·차이·예외만 전달한다. 전체 도구 목록·상태 응답·대형 분류 원문을 출력하지 않는다. 원문은 비공개 증거로 보존하고 필요한 도구의 현재 입력 형식과 응답 필드만 읽는다.
- 병렬 작업자는 겹치지 않는 범위와 필요한 파일·질문·완료 조건을 전달받는다. 이미 확인된 긴 이력·전체 원시 자료를 반복 전달하지 않고, 결과는 근거 경로와 핵심 차이로 합친다.
- 환경 준비·REA 질의·번역·글꼴·화면 검수·패키징의 구분을 기존 명세와 로그에 남긴다. 세션 누적 토큰은 한 번만 집계하고 부모/자식 승계·중복을 확인한다. 캐시는 입력의 일부, 추론 출력은 출력의 일부이며 별도 재합산하지 않는다. 기록 누락과 단계 혼합은 명시한다.
- 도구 호출시간 합, 병렬 작업의 실제 경과시간, 모델 토큰, 실제 청구액은 구분한다. 계측 자체를 별도 대형 도구 개발이나 과거 전체 세션 반복 조사로 확대하지 않는다.
- 대표 본편·저장/불러오기·최종 수정본·최종 ZIP 설치 복구 확인에 필요한 시간을 먼저 계획한다. 조사 범위를 넓히기 전 예상 효과와 남은 검증을 비교한다. 기존 G0~G8, UNKNOWN 처리와 영향 범위 검증은 그대로 유지한다.

### 9.3 변경 영향에 따른 검사 재사용

| 변경 내용 | 다시 확인할 범위 |
|---|---|
| 번역 한 항목 | 해당 위치·토큰·용어·필요 문자, 연결된 글꼴·화면, 후보·패키지 해시 |
| 글꼴·재질·폴백 | 영향받는 모든 사용 위치와 글자 집합, 그래픽 화면, 관련 묶음·카탈로그 |
| 원본 빌드·추출기·분류 규칙 | 파일·객체·오류 목록과 판정 재확인, 영향을 받는 번역과 하위 게이트 |
| 코드·런타임 조합 방식 | 문자열 참조·메서드·화면·저장 경계와 관련 회귀 검사 |
| 설치기·패키지 내용 | 차이 파일·허용 목록·최종 ZIP과 G7~G8 |
| 설명 문서만 변경 | 문서 링크·상태·명세 일관성. 배포 ZIP에 포함되면 G7~G8도 재실행 |

- 검사 결과 재사용은 관련 입력·규칙·도구 버전과 출력 해시가 같고 의존 관계가 완전할 때만 허용한다. 새 빌드에 재사용한 근거를 명시하며 옛 보고서의 빌드 ID를 고쳐 쓰지 않는다.
- 영향 관계가 불분명하면 범위를 넓혀 재검증한다. 최종 패키지의 현재 해시·허용 목록·설치 결과 확인은 생략하지 않는다.
- 결함을 발견하면 같은 출처·규칙·글꼴·화면군까지 조사한다. 제보된 한 문구만 고치고 끝내지 않는다. 결함 재현 → 공통 원인 수정 → 관련 검사 → 최종 산출물 순서로 진행한다.
- 이미 통과한 검사를 이유 없이 반복하거나 과거 문서를 매번 전부 읽지 않는다. 다음 작업을 결정하는 데 필요한 상태·증거·차이만 먼저 읽는다.
- 실패마다 증상·원인·수정·재현 사례·영향 범위를 한 건으로 남긴다. 해결은 문서 작성이 아니라 정상·오류 입력에서 기대 결과가 확인됐을 때 표시한다.

## 10. 완료 보고와 인수인계

마지막에는 결과, 지원 빌드·패치 버전, 수행한 검사와 범위, 유지한 표기·미디어, 미검증 항목, 설치·제거 방법, ZIP 해시, 다음 작업을 전달한다. 원본·후보 자산 없이 재현 가능한 도구·번역 원본의 위치와 실행 순서를 남긴다.

완료 표현은 `정적 검증 완료`, `첫 화면 그래픽 QA 완료`, `기재된 대표 흐름 검증 완료`처럼 증거 범위에 맞춘다. 텍스트 레이어와 이미지·영상 픽셀 한글화를 구분한다. 전체 회차·분기를 확인하지 않았다면 `완벽 한글화`, `전체 실행 QA 완료`라고 단정하지 않는다.

`PROJECT_STATUS.md`는 현재 요약, 게임별 결과 보고서는 해당 빌드의 증거, `WORK_LOG.md`는 변경 이력이다. 과거 보고서는 당시 사실로 보존하고 새 상태를 덧붙인다. 검증 도구가 구현되지 않은 항목을 문서가 보완됐다는 이유로 `PASS`로 바꾸지 않는다.

## 11. 작업 사본의 보관과 정리

게임 파일의 사본과 다시 만들 수 있는 산출물은 증거가 아니다. 증거는 해시 목록, 로그, 캡처, 요청·응답 기록, 보고서다. 사본은 필요한 동안만 두고 지운다.

| 자료 | 위치 | 보관 |
|---|---|---|
| 원본 기준선 사본 | `source_original/<game>/<baseline>` | 그 게임의 패치 작업이 끝날 때까지. 끝나면 사용자에게 묻고 지운다. 파일 목록과 해시는 남긴다 |
| 설치 백업 | `source_original/<game>/installation_backup` 또는 게임 폴더 안 | 지우지 않는다. 설치본을 원본으로 되돌리는 수단이다 |
| 추출 자료 | `extracted_private/<game>/<baseline>` | 위치별 목록·오류 대장·판정 근거는 남긴다. 다시 뽑을 수 있는 대량 자산은 패치 작업이 끝나면 정리 대상이다 |
| 번역 원본 | `working_private/<game>/translation` 또는 `tasks/<game>/translations` | 지우지 않는다 |
| 검수·시험용 게임 사본 | `working_private/<game>/<run>` | 그 검수나 시험이 끝나면 지운다 |
| 보고서·로그·캡처·해시 기록 | `working_private/<game>/<run>`, `validation/<game>/<build_id>` | 지우지 않는다 |
| 후보 | `build_candidate/<game>/<build_id>` | 최신 통과본 하나. 새 후보가 G4를 통과하면 이전 후보를 지우고 해시와 build 기록만 남긴다. 같은 ID로 덮어쓰지 않는다 |
| 배포 패키지 | `release_output` | ZIP은 남긴다. ZIP을 풀어 둔 폴더는 최신판 하나만 둔다 |

- 게임 파일을 복사하기 전에 프로젝트 드라이브의 여유 공간을 확인한다. (게임 크기 × 만들 사본 수) + 20GB보다 적으면 복사하지 않고 먼저 정리한다.
- 번역 원본이 있는 폴더는 정리 대상이 아니다. `working_private/<game>` 폴더를 통째로 지우지 않는다. 게임 작업을 마칠 때 번역 원본의 위치를 게임 README에 적는다. 2026-11-17 조사에서 21개 게임 가운데 14개는 전용 번역 파일을 찾지 못했다.
- 시험 도구가 실행 중에 만든 사본은 도구가 스스로 지운다. 그 밖의 삭제는 목록과 용량, 지웠을 때의 영향을 사용자에게 보여 주고 승인받은 뒤에 한다.
- 삭제 전에 남길 최신 후보와 최종 ZIP의 해시가 기록과 일치하는지, 삭제 대상을 도구나 문서가 입력으로 읽지 않는지 확인한다.
- 삭제한 경로, 확보한 용량, 보존한 것, 재실행 시 영향을 `WORK_LOG.md`에 남긴다.
- 게임 작업을 마칠 때 남은 사본과 용량을 보고한다.
